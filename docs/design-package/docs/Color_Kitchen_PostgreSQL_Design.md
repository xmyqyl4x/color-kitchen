# PostgreSQL design


## Evidence and scope

The production plan assumes an existing shared PostgreSQL service. Confirm the destination and migration owner before any shared-system migration. Develop and test against disposable PostgreSQL while that evidence is pending. The reviewed target repository at commit `e30ea886dfc07fa05067c551ffeabe5b863d9140` contained a README. It provided no migration history, application models, database connection or schema dump. That establishes which evidence was available in the checkout. The database may be managed by another project. No live PostgreSQL relation, authentication provider, database version or account key has been verified. The following names describe proposed additions and contracts. [Repository snapshot](https://github.com/xmyqyl4x/color-kitchen/tree/e30ea886dfc07fa05067c551ffeabe5b863d9140)

Phase 1 stores public reference content, approved localized content, anonymous popularity aggregates and contact requests. Generation history, user images, private palettes, font sample text and local collections remain in the browser. Phase 2 adds authenticated developer projects holding color palettes and role-mapped game themes, private revision history and an owner-controlled release with project or public visibility. Mobile web and the AI connector consume the same application services. A save from the mobile site uses the same project permissions as a save from the desktop site.

## Existing schema review before migration

Run the accompanying `schema_inventory.sql` through an existing authorized read-only connection to the intended database. The script targets PostgreSQL 12 or later for catalog field compatibility. Verify the actual major version and support status before implementing migrations. The script uses a repeatable read, read-only transaction, short local timeouts, catalog-qualified search path and deterministic sorting. It reports object names, column types, key pairs, index order, row security flags, policy and trigger names, installed extensions and candidate migration ledgers. It does not read application records, password data, stored expressions, or function bodies. Treat the output as internal architecture metadata. [PostgreSQL system catalogs](https://www.postgresql.org/docs/current/catalogs-overview.html)

Record one row per candidate in the implementation PR. Capture the actual schema and relation, verified key type, columns needed, owning application, migration authority, tenant boundary, authorized read/write path, deletion behavior and decision to reuse, adapt or extend. Review actual migration definitions with their owner where catalog names and flags cannot establish semantics. Match foreign keys by every column in order. Confirm that a candidate `users` table represents accounts and that its key is stable across provider and email changes. Test account disablement and current project authorization with synthetic fixtures in an authorized staging environment. An inventory run under limited schema visibility cannot establish that an object does not exist.

If an identity consists of multiple tenant/key columns, preserve that entire key in every membership and ownership foreign key. For identities managed outside this database with no local principal mapping, request the owner-approved adapter for `(issuer, subject, tenant)` and resolve it centrally. If a local mapping must be introduced, store only that mapping under the shared identity owner with a unique external tuple. Do not create a `ck.users` table or allow public self-assignment of roles. Work on Phase 1 can continue while Phase 2 identity reuse is being verified.

## Database conventions and boundaries

Use the proposed `ck` schema if the database owner approves it and the namespace is available. Prioritize existing compatible tables and conventions. Supply UUIDs from the application or the database's already approved generator. No new PostgreSQL extension is required for this design. Timestamps are `timestamptz` in UTC. The names `subject_key` and `actor_key` in the tables below stand for the verified canonical identity key and type. Supply tenant keys alongside them if needed. `?` denotes a nullable column. Other fields are required unless stated otherwise. PK, FK and UQ denote primary key, foreign key and uniqueness.

Separate schema ownership/migrations, public reads, trusted application writes and maintenance tasks. Browsers and connectors reach the application API. They never receive database credentials. Server writes use parameterized statements and scoped service roles. Prefer the existing transaction and authorization pattern. Use a restricted write routine or equivalent mutually exclusive transaction path for operations that maintain cross-row invariants. Revoke direct table writes from roles that should only use those operations. PostgreSQL `CHECK` constraints enforce conditions on the current row. FK/unique constraints and locked transactions enforce cross-row rules. [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)

## Phase 1 public catalog and localization

The catalog needs searchable, stable identities and reproducible public revisions. Use one typed revision record per item instead of a separate CRUD service per tool. Filter, sort, join and authorize using relational columns. Keep bounded, validated tool-specific content in `jsonb`. Original photos, uploaded game assets, binary fonts and model conversations do not belong in these records. Each proposed table below is conditional on the shared-schema review.

|---|---|---|
| `ck.catalog_item` | `item_id uuid PK`, `kind text`, `slug text`, `published_rev integer?`, `featured_rank integer?`, `row_version bigint`, `created_at timestamptz` | `kind` in palette, gradient, color, font, template, policy. UQ `(kind,slug)`. Slugs match `^[a-z0-9]+(-[a-z0-9]+)*$` and max 100 chars. Composite FK `(item_id,published_rev)` to revision, deferrable. Null means no public version. Nonnegative featured rank, with stable item-ID tie break. |
| `ck.catalog_revision` | `item_id uuid FK`, `rev integer`, `schema_version smallint`, `edit_version bigint`, `payload jsonb`, `origin text`, `source_uri text?`, `source_version text?`, `license_id text`, `license_uri text?`, `attribution text?`, `source_digest text?`, `created_at timestamptz`, `effective_at timestamptz?`, `sealed_at timestamptz?`. | `ck.tag_text` | `tag_id uuid FK`, `locale text`, `label text`. PK `(tag_id,locale)` | Allowed five locale codes, nonblank label. Populate all five labels before assigning tag to a public entry. For palette JSON require two through twelve swatches with unique local IDs, validated color values in specified color spaces, alpha in `[0,1]`, optional locks and a role-to-swatch map with no dangling references. Color items hold a reference value and canonical color space. Gradient revisions store geometry, two through twelve ordered stops with positions `[0,1]`, interpolation and hue handling. Tied positions preserve declared order. Font records hold source family ID, script coverage, weights/axes and an allowlisted download URL or original verified reference. Keep each family's licenses, notices and required attribution. Templates reference versioned, first-party renderer IDs with supported roles. The four versioned notices use kind `policy` and the stable slugs `licensing`, `terms`, `privacy` and `cookies`. Release requires all translated bodies and a shared `effective_at` at or before publication. Cookie preferences, advertising inquiries and contact are application workflows. Reject unsupported schema versions, nonfinite components and unknown executable or external-rendering fields. Propose a 64 KiB canonical UTF-8 payload ceiling per catalog or project revision. Check encoded request sizes before parsing. These limits are engineering defaults to validate on actual data and devices.

Ship version-controlled interface message bundles for `en`, `fr`, `es`, `pt` and `de`, including metadata, forms, errors, validation messages, ARIA announcements, cookie choices, export controls and privacy text visible on each surface. `pt` is neutral Portuguese. Preserve the requested five locales when the browser sends a regional variant by negotiating to its supported base language. CI requires identical key sets, parameter names and plural/message format validity across each bundle. Localized catalog content joins by `(item_id, rev, locale)` without appending locale-specific IDs to colors, values or project IDs. Human-entered project names and private drafts retain their original language.

**Publication transaction.** Seeded release imports in Phase 1 and the Phase 2 admin publishing service use the same write path. Lock the catalog item row, compare the expected item row version and reviewed draft edit version, validate the candidate payload against its kind and schema, read its translations, verify the exact five locales, validate the license fields, verify five labels for each assigned tag, and check the effective time for a policy revision. Seal the candidate and move `catalog_item.published_rev` and increment `row_version` in one transaction. Keep the previous head if any validation fails. Prevent modification or deletion of sealed revisions/text/tag links through restricted writes and a parent-row guard trigger that also acquires the parent lock. Draft content and child edits acquire the same parent lock and increment the draft edit version before commit. A stale reviewed version returns 412 and requires a new review. The staff publisher's approval commits with publication and audit. Tag label maintenance permits replacement of existing labels, but deletion affecting a published item is rejected. The release's pointer and all five translations become visible together. Withdrawing an item clears its pointer while preserving review history. A content-only rollback moves the pointer to an earlier complete sealed revision and records the reason.

**Storage and read paths.** Make the public repository/view join to `catalog_item.published_rev` first so a query cannot enumerate unsealed drafts. Add a partial B-tree on `(kind, featured_rank, item_id)` for published items, and `(locale, item_id, rev)` on text only if plans show benefit beyond join keys. Test `EXPLAIN (ANALYZE, BUFFERS)` with synthetic representative data and realistic filter combinations in staging. Use prefix/exact searches first. Add a language-aware text index only when representative plans show a need. Avoid a blanket GIN index on all payloads. Restrict tag FKs and the default deletion of published catalog roots. Draft cleanup may cascade through draft text and tag links after confirming no publication points at that revision.

## Popularity and contact requests

| Proposed table | Fields and keys | Behavior and access |
|---|---|---|
| `ck.usage_day` | `item_id uuid FK`, `day_utc date`, `action text`, `event_count bigint`. PK `(item_id,day_utc,action)` | `action` initially `open_in_studio`. Counter starts at zero and stays nonnegative. Index `(day_utc,action,item_id)` for ranking by time window. Retain proposed 90 days. |
| `ck.usage_receipt` | `event_id uuid PK`, `item_id uuid FK`, `action text`, `occurred_day date`, `expires_at timestamptz` | One short-lived receipt per accepted, consent-permitted public interaction. Token binds ID, item, action and original UTC day. Index `expires_at`. No user, session, IP, email or tracking cookie required in these tables. |
| `ck.contact_request` | `request_id uuid PK`, `purpose text`, `locale text`, `reply_email_cipher bytea`, `message_cipher bytea`, `key_id text`, `state text`, `created_at timestamptz`, `closed_at timestamptz?`, `purge_at timestamptz`, `input_hmac bytea`, `hmac_key_id text`, `delivery_state text`, `attempt_count integer`, `next_attempt_at timestamptz?`, `lease_token uuid?`, `lease_until timestamptz?`, `delivered_at timestamptz?`, `provider_ref text?`, `last_error_code text?` | Purpose in support, accessibility, advertising, privacy, licensing. Locale in the five codes. Status in received, in_progress, closed. Closed timestamp set exactly when closed. Index `(state,created_at,request_id)` for authorized support work and `purge_at` for expiry. Claim index on `(delivery_state,next_attempt_at,request_id)`. Nonnegative attempts. A sending row holds both lease fields. Other states have neither. Only a sent row has a delivery timestamp. |

Use a signed, short-lived single-action nonce for a counted explicit catalog open. Preserve the same nonce across a retry. The verifying endpoint checks expiry, signature, item/action binding and consent policy, then inserts a receipt with `INSERT ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id`. Only a successful new insert increments the day row via atomic upsert in the same transaction. For a repeated matching receipt return the same accepted outcome without increment. Reject a key bound to a different item/action. Reject expired tokens before consulting the receipt table, and retain receipts until expiry plus a clock/retry margin, such as 48 hours for a 24-hour nonce. No per-user uniqueness is promised. Do not count denied analytics consent or disabled instrumentation. Show the ranking as observed accepted uses, not unique people or saves. Apply the [functional ranking contract](Color_Kitchen_Design_Specification.md#pub-02--palette-gallery). Evaluate the 25-event, five-palette threshold across currently published palettes before applying filters. Rank the preceding 30 complete UTC dates and break ties by item ID. When the threshold is unmet or measurement is disabled, serve Featured and report the effective sort.

**Idempotent intake.** The client supplies one random request UUID for a submission and retries with that same ID. Canonicalize the purpose, locale, address and message. Store an HMAC over these fields using an application secret, with the key version so a retry after rotation can be verified. Encrypt the address and message with the approved facility. Insert the `received` case and `queued` delivery state in the same transaction. A duplicate key with an identical request returns the same generic acceptance and reference, without exposing contact data. Different content under that key returns HTTP 409 and performs no second delivery. If intake fails, acknowledge only after a successful retry. Keep the published API retry window at 24 hours and retain the submitted receipt for at least that interval. The client must generate a new request ID for a new submission. Document the finite deduplication guarantee and treatment of intentionally erased records.

**Claim and delivery.** Support case status and notification delivery status are separate. Queue states are `queued`, `sending`, `retry`, `sent` and `needs_review`. A worker claims a due queued/retry row with `FOR UPDATE SKIP LOCKED`, assigns a fresh lease token and expiry, increments its attempt count and commits. Send after commit with a stable provider idempotency key derived from `request_id`. A result updates the row only while its lease token still matches, then releases the lease. Record a bounded provider receipt or safe error code. A classified transient failure schedules bounded backoff, for example five total attempts, within the provider’s deduplication window. After a lease expires or a send outcome is ambiguous, retry automatically only with usable provider deduplication or verified delivery status. Otherwise send it to `needs_review` for reconciliation. An accepted case remains in the staff queue. The design does not promise exactly-once external notification without corresponding provider support. Test concurrent claims, a worker crash after remote acceptance, provider ambiguity and expiry.

Operations should confirm the proposed 30-day post-closure purge and 90-day open-case review. Track longer legally required retention for applicable privacy requests separately. Never expose contact text to analytics or ad providers.

## Phase 2 developer projects and themes

A developer explicitly chooses Save to project to move a structured palette or theme from the device into an authenticated project. Preserve the original local document if the save conflicts, the session expires or the network fails. The membership key comes from existing authentication. Keep project access separate from a staff member's right to publish to the curated public catalog. One project may own many assets. Each asset has a linear version history. Releasing an asset is an owner action. Project is the default release audience. Public exposure requires a preview and a separate explicit confirmation.

**Project and member access.** Every protected project or asset query requires an active canonical principal and same-tenant membership. Normal reads and edits require an active project. For an archived asset within an active project, members may explicitly request committed history. Release and connector paths also require an active asset. Through the portal, a viewer can read and export saved revisions, including historical ones. An editor can also create revisions and rename assets. An owner can manage members, archive projects, release a revision to the project or explicitly to the public, and withdraw either release. Connector access is narrower and exposes only an active release of the selected project. Staff catalog curators can draft approved dataset changes; only a staff release permission can publish them. Staff support can access the contact work queue under a separate support permission. Staff status alone grants no private project membership. Existing access-control infrastructure should implement these policy checks and expose the same decisions to website and mobile clients. Where the shared platform uses RLS, add and test tenant/project policies with a restricted client role in addition to API checks. Confirm actual owner/bypass behavior in staging. Keep `owner` membership transfers and removals under a project-row lock. Reject an operation leaving an active project with no owner. On removal/deactivation of a shared account, revoke access immediately and route last-owner transfer or archival through the owner-approved offboarding workflow. Avoid cascading deletion from shared identities into project history.

**Retention and audit.** Keep active projects and immutable revisions until an authorized project deletion or account retention decision. Treat archive as reversible and display the owner-approved hard-delete interval. A purge first withdraws public releases, then removes release rows, clears version pointers and deletes dependent revisions and members in one controlled workflow. The restrictive default FK policy protects shared principals. Backups retire on the shared database schedule. Set an explicit lifetime for administrative audit events, with 180 days proposed for review. Limit retention reads and purges to the audit owner and retain only reviewed reason codes. Protect immutable history with restricted writes and a dedicated retention role.

**Revision shape.** `palette` revisions contain the validated palette object. `theme` revisions contain `tokens` mapping stable machine keys such as `scene.background`, `tile.text`, `action.primary` and `selection.outline` to swatch IDs, plus a supported schema version and the complete referenced swatch values. Require unique keys and exact same-revision targets for every supplied role. Use the [version-one theme role keys](Color_Kitchen_Design_Specification.md#dev-01-game-developer-portal). Drafts can omit bindings. Release requires all six, with values embedded in the same immutable snapshot. Map the known dot-separated keys to collision-free CSS custom properties by replacing dots with hyphens. An asset's historical view never reads mutable colors from the current catalog. Record an optional source catalog ID/revision as provenance and copy the numeric snapshot. Compute JSON and CSS export from a particular revision using a versioned pure encoder. Share only structured fields a user can inspect. Translated display labels and private project names do not enter export unless explicitly selected.

**Concurrent edits and idempotency.** An update includes the expected head revision or ETag and `operation_id` generated once for the attempted save. Within one short transaction authorize the principal, lock the asset row, look up the operation ID under the asset and compare the canonical digest. A matching replay by the original authenticated writer returns the existing revision. Persist a separate `request_hash` on the revision covering asset ID, author, canonical payload and original expected revision, so reuse of an operation ID with changed input returns HTTP 409. Otherwise reject a stale expected head, insert `head_rev + 1` with the validated snapshot and digest, advance head/row version and append required audit. For new assets use a stable application-created `asset_id` and operation key so retries return the same first revision. Acquire locks in project, asset and revision order. Recheck permissions inside the transaction for releases or membership changes. A failed HTTP `If-Match` precondition returns 412 with the authorized current version and a reload or save-copy path. Use 409 for a conflicting domain transition or changed input under the same operation key. Never overwrite someone else's change automatically. Retry transient serialization and deadlock failures only by rerunning the entire transaction with a bounded policy. [Transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

**Release lifecycle.** The project owner selects one saved theme revision and sees the exact role/color payload, version and export before committing. The release form and database default to `project`. A public release requires an explicit audience selection and confirmation that anyone may read it. Persist public releases only through the release operation after server-side owner and confirmation checks. The audience, asset revision and digest remain fixed for the life of the release. The portal preview continues to require current project membership.

**Durable command retries.** For each owner release/withdrawal or staff publication/withdrawal/restore, the client generates one operation key per intentional command. The key is a UUIDv7 whose timestamp supports the published 24-hour acceptance window (allow up to five minutes of future clock skew). Retain receipts at least 48 hours and reject expired operation keys before the mutation path, including after a matching receipt is purged. A new deliberate action uses a new key. Resolve current authorization before exposing any replay. Within a transaction reserve `(actor_key,operation_id)` with `INSERT ... ON CONFLICT DO NOTHING`, then compare the stored command, resource and SHA-256 hash of normalized input, including original precondition, selected revision/release, audience and confirmation. An identical completed replay returns its original HTTP result and release/version ID, even if the original release has since been withdrawn. It performs no mutation. A mismatch returns 409. Replay lookup precedes the `If-Match` check for a new authorized command. A successful reservation, mutation, audit append and final receipt completion commit together. Business errors and crashes roll back the reservation. A deferred constraint trigger re-reads the receipt by PK and checks its final success result at commit, which prevents incomplete receipts from surviving a failed operation. An existing shared receipt mechanism can substitute when it guarantees the same atomicity.

**Fresh publication and withdrawal.** For a new authorized command, lock project then asset, recheck owner status, and compare `If-Match` to the current asset/release version. Return 412 if stale. Withdrawal names the exact active release and cannot affect a later replacement. A conflicting transition with a matching precondition, such as withdrawing an already withdrawn target with a new key, returns 409. A new release withdraws the prior current release, appends a new immutable release ID and increments the asset version, then records audit and receipt before commit. Re-release of the same saved revision and audience after withdrawal is legitimate with a fresh request key, current precondition and explicit public confirmation when applicable. Historical releases stay withdrawn. The only release uniqueness rule beyond the release PK is the partial unique index for one active release per asset. Staff catalog publication and rollback use the same receipt/precondition rules against a monotonically increasing catalog item row version, including rollback to an earlier revision.

Anonymous theme reads by release ID require an active project, active theme asset, `audience='public'` and `withdrawn_at IS NULL`. Anonymous catalog reads instead follow the published catalog pointer. Serve every theme lookup with `Cache-Control: no-store` and exclude theme release endpoints from search indexing. Archiving an asset or project withdraws its active releases in the same transaction. Restoring the asset or project leaves those releases withdrawn. A new publication requires an explicit owner action. Exported copies already downloaded are outside server access controls.

## Connector and clients

Phase 2 includes two read paths through the shared application services. A public catalog tool works anonymously and reads only published catalog records. Any public theme-release read uses the same explicit public-release predicate. A project connector authenticates through the shared identity provider, requires OAuth scope `project:read`, and binds the grant to the nonempty set of projects explicitly selected by the user for that client. On every call, verify issuer, audience, signature, expiry, scope, active canonical subject and current membership of that exact project. Require an explicit project ID and theme asset ID. Read only that asset's active, unwithdrawn release and its versioned JSON/CSS exports. Project-authorized access includes a release whose audience is `project`. The query joins the requested project, active asset, current release and matching immutable revision. Neither knowing an asset/release ID nor possessing a valid token establishes project membership. Return the service's uniform unavailable response for unauthorized or absent objects, reject writes, and omit drafts, prior revisions, withdrawn releases, project rosters and unrelated projects. Send `Cache-Control: no-store` for theme reads. A fresh authorization decision checks the current grant, subject and membership without a cached allow. Record the grant client, actor, scope, expiry, revocation and allowed project IDs in the verified provider or its application-side grant mapping. Check current access on refresh and on each read.

The browser extension's deliberate pixel or style capture stays local and explicitly transfers a bounded palette to the website. The mobile-optimized web route and extension use the same export schema. Each client's private storage stays local unless the user expressly saves structured color data to a project.

## Migration, recovery and tests

1. Obtain the approved catalog inventory and matching migration repository from the database owner. Confirm shared keys, tenant semantics, session provider and existing retention/backup settings. Record the reuse map and required grants. Attach sanitized structure findings, never credentials or data dumps, to the schema review.
2. Use the existing migration ledger and lock mechanism. Add the approved schema/tables/constraints in an isolated staging copy. Use additive nullable columns and bounded backfills if extending existing populated tables. For long validations, consider adding supported constraints `NOT VALID` then validating separately. A concurrent index build needs its own migration step outside a transaction. Check resulting indexes for readiness/validity following a failure. [ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html), [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)
3. Seed original catalog revisions and the complete five-locale sets using deterministic stable identifiers and checksums. Replaying the same seed must be a no-op. A changed payload creates a new revision. Catalog migrations do not drop customer or previous application objects. Use a staging fixture for untrusted field text, odd locale negotiation and revoked users. Verify prior application binaries can read the expanded schema before enabling new writes.
4. Deploy read/write adapters under a release flag. Compare imported counts, per-kind/locale checksums and FK/unique coverage to the seed manifest. Enable Phase 1 reads, then independent aggregate/contact writes. Phase 2 first introduces the verified identity and project model, then revisions and export, followed by the release/admin/client paths. Remove superseded columns only after dependent applications, backups and rollback windows permit it.
5. If a rollout fails, disable the feature writer and roll back to the compatible app version, retaining entered data. Repair via an additive forward migration. Restore catalog visibility by repointing to an earlier sealed revision. Reserve destructive rollback or full recovery for an operator-approved incident workflow. Never restore the shared database over unrelated applications to undo one Color Kitchen write.
6. Confirm actual backup method, RPO, RTO, retention, encryption key recovery and primary owner. For planning, propose at most 24 hours data loss and 4 hours recovery for private projects until the database owner approves tighter or existing objectives. Use an isolated restore/PITR target, verify account/project links and authorization without resetting real user records, compare sealed catalog/asset checksums, render a representative export, then transfer only the reviewed recovery changes. Purge expired contacts, receipts and aggregates in bounded batches, with indexes on expiry and deletion counts without private contents. A retention policy also includes backup expiry, logged data and encryption-key retirement. [Backup and recovery](https://www.postgresql.org/docs/current/backup.html)
